# 面试问答话术（M11 交付物，完整版）

> 完整话术脱离对话历史，换机器/换会话可直接取用。
> 原则：**每个结论都挂实测证据**，不背空洞概念；被追问数字必须能说清出处。

## Q1: 为什么用 Playwright 不用 Selenium？

三层回答 + 一句代价：

1. **等待机制（最核心差异）**：Playwright 操作前自动等待（auto-waiting），`expect()`
   自动轮询断言；我的项目登录断言、toast 等待全是"语义等待"，**零固定 sleep**。
   Selenium 要手写 WebDriverWait + expected_conditions，忘了写就 flaky。
2. **定位器更稳**：`get_by_role` / `get_by_label` / `get_by_placeholder` 按"用户怎么找到
   元素"定位，前端改样式不崩；Selenium 惯用 XPath/CSS，改 class 就挂。
3. **工程能力**：内置 Trace 录制（失败可重放，我用来定位保存后竞态）；网络监听
   （`page.on("request")`，我靠它抓到登录接口真实路径）；storage_state 会话复用
   （e2e 免 UI 登录）。
4. **代价（主动讲）**：Playwright 浏览器二进制下载在国内要配镜像（CDN 不可达，
   M1 实测换 npmmirror 解决），已沉淀进 README。

## Q2: API 用例比 UI 多，是不是偷懒不想做 UI？

不是偷懒，是测试金字塔的实测结论，三点：

1. **稳定性**：UI 依赖渲染时序与网络，公网过载时 goto 随机超时（实测 Builder 5P /
   Reviewer 3P+2E 并存）；API 只有 HTTP 往返，不受渲染影响。
2. **断言精度**：UI 断言"看得到什么"（文案/URL），API 断言"业务规则本身"——状态码
   200 不等于业务正确，要看 JSON 结构。（e2e 双向闭环正是在印证这个差异）
3. **成本**：同环境实测 API 层比同规模 UI 快约 3 倍；本地确定性环境比公网快约
   4~9 倍（视时段与用例集，禁止说单点"11 倍"——已被审查否决）。

关键表达：**UI 不是不用，是做关键用户旅程和 E2E 闭环**；金字塔落点是"分层配比"，
不是"砍 UI"。

## Q3: 测试数据怎么管理？共享环境数据污染怎么办？

三件套：

- **数据工厂唯一命名**（`utils/factory.py`：时间戳+前缀，全项目唯一）
- **测试前自建**（绝不断言固定数据——共享 Demo 实测 3 分钟他人造数 +1 条）
- **测试后清理**（finally 里幂等删除，删除前按唯一名重新搜索，容忍 200/404）

追问防御："清理失败怎么办"→ 清理移入 finally 保证执行 + 删除前重查 + 幂等；
项目有"清理真实性核验"：跑完 API 搜索前缀残留 = 0。

## Q4: flaky test 怎么排查和治理？

完整链路（这是本项目最实战的部分）：

1. **先度量**：固定命令 ×N 跑（flake_measure 脚本 ps1/bash 双平台），统计失败率
2. **归因**：区分环境 / 数据 / 定位器 / 时序——公网 goto 超时是环境；Save 后竞态是时序
3. **治理**：环境类→超时校准（wait_until=domcontentloaded）+ 单次重试；时序类→
   业务语义等待（等 toast 而非 sleep）
4. **再度量**：治理前后对照（goto 超时 2/3 → 3/3）
5. **可观测性**：重试计数终端打印——能区分"flaky 消失"与"被重试救回"

**红线**：不无脑重试掩盖问题（AGENTS §14）；重试只吸收环境噪声、不改变断言。

## Q5: 听说过断言 5s 盲区吗？（追问）

Playwright 的 `expect()` 默认超时 5s 且**不受** `page.set_default_timeout()` 影响——
操作层和断言层是两套预算。这个潜伏 bug 是 M5 全量运行公网过载时段才撞出来的。
修复：断言超时统一收敛到 `ASSERT_TIMEOUT_MS = DEFAULT_TIMEOUT*1000`，全仓 5 处
断言点替换。

## Q6: 为什么加 DB 校验层？页面显示成功不够吗？

"页面显示成功"和"数据真的落库"是两回事，API 层也看不到 DB 物理行为。实测两个边界：

- API 创建的员工 employee_id 为 **NULL**（显示编号不走 API 创建路径）
- API 删除后 DB 行**物理消失**（purged_at 软删字段没被启用）——硬删 vs 软删只有
  查库能区分

DB 层用最小权限只读账号（GRANT SELECT，MySQL 侧强制），校验"真落库/真删除"。

## Q7: 谈谈项目的 Review 流程（这是个很有特色的点）

本项目有完整的分模块 Review 门禁（AGENTS.md），也因此踩了两个真实坑：

1. **M0 没 APPROVED 就放行后续模块**（门禁失效）——被全面复审抓到
2. **M6 的审查结论由实现方自己写**（门禁自证）——被所有者作废、状态回退 NEEDS_FIX

第二次事故后我把"审查独立性"写成了制度（AGENTS §13.1）：审查结论必须独立提交、
晚于被审实现、附审查方自有运行数据、**代笔则 APPROVED 作废**。之后每轮复审都是
独立方实测。**面试官很吃这个故事**——说明我不只写测试，还理解质量流程本身。

## Q8: 项目还有什么不足？未来改进？

诚实作答（暴露边界反而加分）：

- CI 真实触发没跑（本地 act 网络不通，上仓后闭环；不宣称"已跑通"）
- flake 度量只覆盖公网场景，requests 层低频瞬态靠重跑判断
- 镜像 2.72GB 偏大（可优化分层/精简）
- 覆盖率未统计（YAGNI——重点是测试有效性而非指标）
- 用例规模 19 偏小（M0-lite 收口时 Leave 模块未展开，计划补 60+）
